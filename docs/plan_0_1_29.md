# 0.1.29 计划：程序图标与签名链路

状态：开发中（main，版本仍为 0.1.28，未打 tag、未公开）。范围与背景：用户决定 macOS/Linux 版暂不依赖 minicon 的 crate，但可以复用其代码模块；签名链路接入 winmgr；同时准备程序图标。参照 [plan_port_macos_linux.md](plan_port_macos_linux.md) §0。

## 1. 已完成（本地可验证）

- [x] 图标：`assets/icon/generate_winmgr_icon.py` 复用 minicon 图标生成器的光栅化与 PNG 写入代码（标准库，可复现），生成 `assets/winmgr.ico`（16、24、32、48、64、256 六个尺寸）。图案为青色窗口框、任务栏与三个任务按钮，激活任务为琥珀色；小尺寸版本只保留两个任务按钮。已在 256 与 32 尺寸下审阅。
- [x] 资源嵌入：`build.rs` 为 `minicon-winmgr` 与 `minicon-tskmgr` 分别嵌入图标与版本信息（产品名、公司名、文件说明、原始文件名），通过 `winresource` 的 `compile_for`。manifest 仍走原有的链接参数，没有重复。本地构建后版本信息正确，资源管理器可取到图标。
- [x] 签名前的构建顺序：`scripts/build_candidate.py` 拆出 `--tool-only` 与 `--signed-tool` 两个阶段。原因：winmgr 把 tskmgr 的哈希编进自身，tskmgr 必须先签名，再用签名后的哈希编译 winmgr。本地用未签名 tskmgr 走通了两个阶段，绑定正确。
- [x] 签名工作流：`.github/workflows/winmgr-signed-candidate.yml`，手动触发，顺序为 构建 tskmgr → 签名 tskmgr → 绑定编译 winmgr → 签名 winmgr → 打包。签名步骤沿用 minicon 的 `azure/login` 与 `Azure/artifact-signing-action` 固定版本，并校验签名状态、时间戳和发布者名称。`guard` 作业在未确认配置前直接失败，不产生未签名输出。现有的 `candidate.yml` 不变，正式发布路径不受影响。

## 2. 需要你开通（我无法代做）

签名要求的 Azure 资源与权限只能由你（或公司账户管理员）开通：

1. Azure 订阅与 **Artifact Signing** 账户，并创建公开信任（Public Trust）的证书配置文件。发布者身份必须与 minicon 一致（PARTNERNET SOFTWARE PTY LTD）；若复用 minicon 的账户与证书配置文件，只需新增 winmgr 的联合凭据。
2. Entra ID 应用注册，添加对 `partnernetsoftware/minicon-winmgr` 仓库 `release-signing` 环境的 GitHub OIDC 联合凭据，角色只授予签名者。
3. 本仓库的 GitHub 配置：
   - Environment `release-signing`（建议设为需要审批）。
   - Environment secrets：`AZURE_CLIENT_ID`、`AZURE_TENANT_ID`、`AZURE_SUBSCRIPTION_ID`。
   - Environment variables：`ARTIFACT_SIGNING_ENDPOINT`、`ARTIFACT_SIGNING_ACCOUNT`、`ARTIFACT_SIGNING_PROFILE`。
4. 配置完成后告诉我，我会先手动运行一次 `winmgr-signed-candidate.yml`（勾选 `confirm_provisioned`），核对结果，再把它接入正式发布。

## 4. 风险

- 签名后的 exe 哈希与未签名版本不同，任何依赖旧哈希的记录都要按签名后的产物重算；本地测得的候选哈希不能直接作为发布依据。
- `Azure/artifact-signing-action` 的目录筛选参数（`files-folder`、`files-folder-filter`）是按其文档选用的，第一次真实运行前需要核对输出。
