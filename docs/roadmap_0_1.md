## 2. Sysmgr 的下一步

用户已明确：Sysmgr 面向整机内存、磁盘、硬件等监控与管理；Tskmgr 专注进程和网络管理。网络分界按进程与设备对象定义，详见 PRD。

Sysmgr 建议先做只读概览：内存压力与提交、CPU/硬件信息、卷容量和磁盘 IO、网卡/链路与接口吞吐。先查证指标来源、权限、设备支持和持续开销，再确定最小可用界面及首发版本。温度、SMART、GPU、清理与设备修改不一并承诺。

不把 Sysmgr 定义为 Tskmgr 的宿主或插件平台；两者可独立运行，共享基础代码并相互定位。没有明确用户问题和可验证范围前，不创建空的后续版本计划。

## 4. 每个阶段的共同交付条件

先在 PRD 明确范围，再实现和验证，最后公开准确候选。保留真实失败、恢复结果和未覆盖环境；不把开发构建、私有交接测试或单纯 CI 成功写成公开更新已完成。

已被后续公开版替代的计划才归档；.16–.18 计划现已归档，当前公开 .19 计划保留在主目录。工具开发不改变 companion 默认、不自动接管外壳，也不提高 Winmgr 常驻权限。

## 5. 跨平台与基础服务的并行演进

用户已确认这些产品应为 macOS/Linux 和未来 computer-use / mind-use（AI/SI、harness、agent、model、modelArgs 等）保留扩展能力，唯一原则见[基础服务 PRD](prd_7_2.md)。这修正了此前只讨论 Windows、未明确长期适配方向的表述；不启动当前 macOS/Linux 移植。

- .15：保持更新修复范围，不为长期架构扩大补丁。
- .16/.17：查询/动作与 GUI 分离、Windows 适配边界、稳定对象身份及结构化结果纳入设计和验收。
- 后续：先选择一个真实自动化使用场景验证少量只读接口，再选择第二平台验证公共模型；无固定版本、时间及功能齐平承诺。
- Sysmgr：从起步就遵循同样能力分层；硬件数据缺失、权限与平台差异必须可表达。
