# 跨平台演进与生产力基础服务

> 稳定索引：7.2。上位：[PRD](prd.md)，产品分工见 [7.1](prd_7_1.md)。更新：2026-10-19。
> 用户已确认长期方向：Windows 上积累的功能与产品应为未来 macOS/Linux 扩展预留边界，逐步逼近；同时作为 computer-use、mind-use 的底层服务。目前未实现跨平台版本或自动化服务。

## 1. 长期目标与近期边界

这些工具属于生产力套件，既面向人直接操作，也为未来 computer-use 和 mind-use 提供可组合的系统能力。AI/SI、harness、agent、model、modelArgs 是上层使用与编排场景，不要求分别实现一套系统管理逻辑。

Windows 是近期交付平台，不是产品能力模型的永久边界。macOS/Linux 按实际可用接口、权限及桌面环境逐步适配，不承诺复制 Windows 外壳形态或所有管理能力。Linux 的发行版、桌面环境及显示协议差异须按实际覆盖标记。

当前不启动完整移植，不承诺支持矩阵或日期（2026-10-28 用户提出策划方向，讨论稿见 [plan_port_macos_linux.md](plan_port_macos_linux.md)，未经确认前仍以本段为准）；近期功能开发必须考虑可拆分的边界，但不为尚未验证的平台预建大量空抽象。

## 2. 建议的能力分层

```text
人类 GUI / 后续 CLI 或结构化接口 / computer-use、mind-use 的调用方
                          ↓
产品能力：窗口定位、进程查询、网络观察、整机资源、明确的管理动作
                          ↓
平台适配：Windows / 后续 macOS / 后续 Linux
                          ↓
操作系统 API、权限授权及硬件数据来源
```

- 产品能力返回结构化数据和结果，界面负责展示与交互；避免把关键查询、过滤、身份判断和操作规则只写在窗口回调中。
- Windows 句柄、SID、令牌、WTS 会话及注册表等留在适配层；跨平台模型保留平台扩展信息，不能假设所有平台都有相同的登录 Shell、用户/会话或提权语义。
- 抽取实际复用部分：采样快照、指标单位和时间、查询/操作结果、主题及交互规则可逐步共享；UI 工具包与语言边界暂不预设，独立进程也不等于强制同一种 UI 技术。
- 进程对象不能仅靠 PID 表示；身份包含运行主机/平台上下文及可校验的生命周期标识。连接、设备、窗口同样需处理消失、复用和不可查询。
- 每项能力可表达支持、受限、需授权、不可用及原因；缺字段与零值分开。不同平台不通过伪造数据或无效按钮获得表面一致。

## 3. 面向 computer-use / mind-use 的服务契约

先把 GUI 使用的内部能力做成可复用接口，再按真实调用需求提供 CLI、进程间协议或其他适配入口；当前不预选 MCP、HTTP、常驻 daemon 或通用插件协议。

未来接口至少明确：

| 内容 | 要表达的事实 |
|---|---|
| 能力发现 | 当前平台、实现版本、支持范围、采样来源和需要的权限 |
| 查询上下文 | 原用户、会话、筛选目标、数据时间与是否部分可得 |
| 操作请求 | 明确动作与目标身份、调用方权限、授权范围 |
| 生命周期 | 超时、取消、目标已消失、处理中和最终结果 |
| 结果 | 成功、失败、部分成功或需要授权，以及可解释原因 |

权限主体与原始用户不能因 AI 调用或管理员凭据改变而混淆。GUI、CLI 和 agent 对同一动作复用同一套校验；自动化入口不隐式继承无限管理权限。授权方式随平台与调用环境适配，不能把 Windows UAC 当作通用协议字段。

查询默认按需、有界；将来订阅数据时定义采样频率、取消、丢弃旧快照和资源上限。共享能力不意味着所有工具或模型都自动获得网络服务入口。

原始命令行、网络端点等数据可能包含用户信息，默认留在明确请求的本机查询范围；不自动上传给 model 或遥测系统。日志记录操作与错误所需信息，避免复制完整敏感参数。

## 4. 演进顺序

1. **Windows 交付阶段**：.15 完成更新修复；Tskmgr 首期将查询/动作与界面拆开，平台代码集中；为未来调用方保留可复用的数据与错误结构。
2. **服务契约阶段**：有第一个实际 harness/agent 使用场景后，选少量只读查询验证结构化接口、取消与能力发现；再按需求扩展管理动作。与新 GUI 功能分开验收。
3. **第二平台验证阶段**：选择 macOS 或 Linux 的一个实际用户场景，优先移植只读进程、资源或网络查询；对比权限、语义与采样开销，修正公共模型。
4. **逐步补齐阶段**：依据真实限制与用户价值扩展管理和窗口集成，保留平台特有能力，不以一次性功能齐平作为发布前提。

后两阶段尚未选择平台、版本或日期。需保留适配能力，不为凑齐平台数量创建空计划、驱动或常驻服务。

## 5. 验收原则

Windows 首期需能识别平台适配边界，核心数据/操作规则可在无 GUI 条件下验证；不要求现在引入完整通用框架。实际平台适配必须在对应系统记录运行与权限证据，模拟接口不能宣称已支持该平台。

未来自动化入口要覆盖目标身份变化、授权取消、超时与部分失败；操作返回受理不等于执行成功。能力、版本与结果必须可供调用方判断，不能只提供面向人的弹窗或解析界面文本。
