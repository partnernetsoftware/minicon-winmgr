# prd_1_1_3 — 更新分发优化

> 索引：1.1.3 · 上位：[`prd_1_1.md`](prd_1_1.md) · 目标版本：0.1.24（设计稿，未开工）
> 状态：0.1.24 实施范围已定（§7）。§6 的决策由开发代理按保守原则决定，用户可以改。

## 1. 背景与问题

当前手动更新（Check → Update → Restart）的链路是：

1. Check：请求 `api.github.com` 的 latest 接口，得到版本与资产地址。
2. Update：先下载 `SHA256SUMS.txt`，再从 `github.com/.../releases/download/...` 流式下载裸 `minicon-winmgr-vX.Y.Z-x86_64-windows.exe`，边写边校验 SHA-256。
3. Restart：由临时助手替换文件、核对启动回执。

存在两个问题：

- **下载慢甚至不可达**：GitHub Release 附件在中国大陆网络下速度不稳定（经调研，GitHub 没有官方的国内加速节点；社区反馈见 [jsDelivr issue](https://lightrun.com/answers/jsdelivr-jsdelivr-support-to-download-github-release-assets) 与 [Discourse 讨论](https://meta.discourse.org/t/topic/410639)）。当前代码把资产地址与 API 地址写死为 GitHub，且严格比对前缀，任何镜像都会被拒绝。
- **发布格式只有裸 exe**：每次更新都传输完整可执行文件，没有可压缩的发布包，也没有随包的清单，后续无法在一个附件内携带多文件（例如工具与校验信息）。

## 2. 目标

- G1 **可达性**：在 GitHub 直连困难的网络下，更新仍可以完成；传输来源可以替换，但不能降低完整性保证。
- G2 **发布包为 `.zip`**：官方发布的主附件是 zip；客户端自行解压，**使用 Rust 解压 crate，不调用系统工具**（`tar`、`Expand-Archive`、7-Zip 等均不采用）。
- G3 **稳定与低内存**：下载与解压都是流式的；解压缓冲固定大小；对条目数、单文件大小、总解压大小设置上限；拒绝路径穿越、绝对路径、符号链接与设备文件。
- G4 **完整性不降级**：更新程序只安装经过校验的内容。传输来源不被信任，校验依据必须来自独立信任锚。

非目标：不改变“检查不自动联网、更新需用户点击”的原则；不改变普通权限、不请求 UAC、不改变替换助手的回执与回滚语义。

## 3. 功能要求

### 3.1 发布包

- 每个版本发布主附件 `minicon-winmgr-vX.Y.Z-x86_64-windows.zip`，内含 `minicon-winmgr-vX.Y.Z-x86_64-windows.exe` 与 `BUILDINFO.toml`（内容与现有清单一致）。
- 校验文件 `SHA256SUMS.txt` 同时列出 zip 与 exe 的 SHA-256。
- 过渡期：旧客户端只认识裸 exe 资产，因此在停止发布裸 exe 之前，每个版本同时附带 exe（见 §6 决策 D4）。

### 3.2 客户端解压

- 使用 `zip` crate（需确认版本、许可与最小特性集，仅启用 deflate）读取中央目录，流式解压单个预期条目到暂存目录。
- 只接受一个预期的 exe 条目，名称必须与版本匹配；其他条目一律忽略或拒绝（以实现时的白名单为准）。
- 上限：压缩包大小 ≤ 64 MiB（沿用现有 `MAX_EXE` 量级），条目数 ≤ 16，解压后总大小 ≤ 64 MiB。超过即失败并清理暂存。
- 条目名必须是纯文件名：拒绝绝对路径、盘符、`..`、目录分隔符、符号链接属性。
- 解压失败、校验失败或超限时，保留旧版程序，清理本次暂存文件（沿用现有 staging 清理语义）。

### 3.3 完整性

- 先校验 zip 本身的 SHA-256（来自 `SHA256SUMS.txt`），再解压，再校验解出的 exe 的 SHA-256（与 `BUILDINFO.toml` 或同一清单一致）。
- 校验依据必须来自信任锚（见 §3.4），不能只靠与资产同源的 `SHA256SUMS.txt`。

### 3.4 信任锚（前提条件）

- 在允许任何镜像之前，必须有独立于传输来源的签名：发布时对 `SHA256SUMS.txt` 生成签名文件，客户端内嵌公钥验证签名。
- 签名算法与库待定（候选：Ed25519 与 `ed25519-dalek`，或 minisign 格式与 `minisign-verify`）。
- 签名私钥由发布流程持有，不进入仓库，不进入普通构建产物。私钥保管与轮换方式见 §6 决策 D3。
- 没有签名时，镜像只能作为仅限手动使用的离线分发方式，不作为自动更新源。

### 3.5 下载来源（可达性）

- 更新源是有序列表：先用配置的首选源，失败后依次尝试备选源；每个源的失败原因分别记录。
- 首选与备选源必须是**显式配置**（配置键待定，例如 `update.source`），默认仍为 GitHub 官方地址；不自动访问第三方服务。
- 版本发现（latest 查询）也可以从固定的清单文件获取（例如 `latest.json`，同样签名），以减少对 `api.github.com` 的依赖；是否启用见 §6 决策 D2。
- 任何来源返回的内容都先经过签名与哈希校验，来源本身不作为信任依据。

### 3.6 性能与内存

- 下载、解压、校验均使用固定大小缓冲（沿用 16 KiB 量级的分块），不将整个包读入内存。
- 进度沿用现有进度回调；解压阶段也要有进度与取消检查。
- 原型须实测：zip 解压峰值内存、耗时与 exe 体积增量（`zip` crate 的依赖体积）。

## 4. 验收

- 单元：zip 解压的正反例（正常条目、路径穿越、绝对路径、符号链接、超大条目、超条目数、截断/损坏档案）；签名验证的正反例；来源列表的回退顺序。
- 集成：用公开旧版（0.1.23）作为更新器，从 zip 发布包完成更新、重启、回执核对；损坏 zip 与错误签名时保留旧版。
- 发布：候选构建产出 zip 与签名；草稿比对逐字节；公开后真实更新探针通过。
- 资源：原型实测峰值内存与耗时写入验收记录。

## 5. 不做

- 不调用系统解压工具或 PowerShell `Expand-Archive`。
- 不在检查更新时下载或解压。
- 不内置第三方镜像作为默认源。
- 不改变 Winmgr 与 Tskmgr 的权限边界。

## 6. 待决策（必须先由用户确认）

- **D1 镜像主机**：是否由项目方自建国内可达的分发点（对象存储、Gitee Releases 同步或其他），还是只支持用户自行配置的代理。影响成本、运维与隐私说明。
- **D2 版本发现**：是否引入签名的 `latest.json` 清单，替代对 `api.github.com` 的依赖。
- **D3 签名与私钥**：签名算法；私钥由谁保管、在哪个环境签名；如何轮换与吊销；丢失时的应急方案。没有此决策，不实施任何镜像。
- **D4 过渡策略**：0.1.24 是否同时发布裸 exe（推荐：是，直至旧版本基本退出）；裸 exe 停止发布的版本号由用户指定。
- **D5 工具打包**：Tskmgr 是否进入同一个 zip。影响工具离线使用与 `tool_entry_probe` 的验收路径，需与 0.1.16–0.1.18 的双产物约定一致。

## 7. 0.1.24 已定范围（开发代理决定，待用户确认）

| 决策 | 结论 | 理由 |
|---|---|---|
| D1 镜像主机 | **本版不做**自建或第三方镜像；来源列表留到签名落地后 | 无签名时镜像不可作为自动源；自建分发点有成本与运维，需要单独决定 |
| D2 版本发现 | **不变**，继续用 `api.github.com` | 清单文件必须签名，依赖 D3 |
| D3 签名与私钥 | **本版不做** | 私钥保管与轮换必须由用户决定，开发代理不生成或保管签名私钥 |
| D4 过渡 | 每版**同时**发布 zip 与裸 exe | 0.1.23 及更早客户端只认 exe 资产 |
| D5 工具打包 | Tskmgr **不进** zip，沿用现有独立附件 | 避免改变工具离线与下载验收路径 |

因此 0.1.24 交付的是：**zip 发布包 + 客户端用 `zip` crate 解包**。G1（国内可达）在本版**不达成**，发布说明与验收记录必须明示，不得声称国内下载已改善。

- 发布包：`minicon-winmgr-vX.Y.Z-x86_64-windows.zip`，内含且仅含同版本 exe（同名条目）。`BUILDINFO.toml` 在 zip 外部，记录 `zip_sha256`，避免 zip 与清单互相依赖。`SHA256SUMS.txt` 同时列出 zip 与 exe。
- 客户端：优先使用 zip 资产；zip 缺失时回退到 exe 资产（兼容旧发布）。zip 先整体下载到安装目录内的暂存文件并校验 SHA-256，再流式解出唯一的 exe 条目，最后沿用现有暂存、校验与替换流程。
- 解包限制：条目数 ≤ 16，唯一预期条目名必须与版本匹配，拒绝绝对路径、盘符、`..`、目录分隔符与符号链接，单条目与总解压大小 ≤ 64 MiB，超限即失败并清理。
- 暂存清理：zip 暂存文件在成功、失败、取消三种路径下都删除。
