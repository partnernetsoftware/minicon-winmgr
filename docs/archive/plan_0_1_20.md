# 0.1.20 计划：任务栏全屏让位

状态：已合 main 并公开交付（2026-10-21）。准确候选、公开附件、真实 .19 → .20 更新及同版工具下载通过，证据见[验收记录](validation_0_1_20.md)。用户报告真实缺陷：mstsc 连接远程服务器选"全屏"后基本没有效果——任务栏仍压在全屏窗口之上。需求回写见 [prd_1_1.md](../prd_1_1.md) 任务栏节；原 0.1.20 采样证据讨论稿顺延为 [0.1.26](plan_0_1_26.md)。

## 1. 用户问题与根因

任务栏窗口以 `WS_EX_TOPMOST` 创建并在重停靠时维持置顶，但没有任何"全屏应用让位"机制：AppBar 模式忽略 `ABN_FULLSCREENAPP` 通知，外壳模式（无 explorer）没有自检。系统自带任务栏的行为是：某显示器上激活全屏应用时，该显示器的任务栏降至 z 序底部，退出全屏后恢复。缺失该机制导致 mstsc 全屏、全屏视频、游戏等场景任务栏永远压住一条边。

.20 的目标：全屏前台应用所在显示器的任务栏自动让位（退出置顶、降至底层），应用退出全屏或焦点离开后自动恢复；其他显示器任务栏不受影响。

## 2. 任务树

```text
.20 全屏让位主线
├── [x] 全屏判定（可单测的纯函数）：前台窗口矩形完整覆盖其所在显示器
│       排除：本进程窗口、桌面宿主（Progman/WorkerW）、最小化/不可见窗口
├── [x] 按显示器让位：命中显示器上的任务栏退出 topmost 降至底层，只改 z 序
├── [x] 自动恢复：前台不再满足全屏条件时恢复 HWND_TOPMOST；状态迁移不抖动
├── [x] 事件驱动 + 兜底：复用现有 WinEvent 防抖刷新评估全屏状态；时钟周期兜底
├── [x] AppBar 模式处理 ABN_FULLSCREENAPP 通知，与自检结论一致
└── 发布闭环
    ├── [x] 质量门禁与定向验证（含隔离桌面实际全屏窗口路径，开发构建与准确候选各一轮）
    ├── [x] 准确候选晋升与公开附件：四附件与候选逐字节一致，公开为 Latest
    └── [x] 真实 .19 → .20 公开更新及同版工具下载通过，原桌面恢复
```

## 3. 实施约束

- 让位只调整 z 序，不隐藏任务栏窗口、不注销 AppBar、不改动工作区保留——全屏窗口本就不使用工作区，改保留反而影响其他最大化窗口。
- 判定与状态更新只在消息线程进行，遵守"taskbar 状态只允许消息线程访问"不变量；判定本身不做文件/跨进程 IO。
- 多显示器按 bar 所在显示器独立让位；让位期间不主动弹出悬停气泡/预览（bar 在底层收不到悬停即可，不另加状态）。
- 不新增线程、不新增常驻轮询；评估挂在既有防抖刷新与时钟节拍上。事件缺失时恢复延迟最长一个时钟节拍（5 秒），记录为已知边界。
- 不把"前台最大化窗口"误判为全屏：最大化窗口受工作区约束，不覆盖任务栏区域，判定天然不命中；保留单元用例锁定。

## 4. 测试分层与停止条件

| 风险 | 最小验证 | 复用 |
|---|---|---|
| 全屏误判（最大化/普通窗口触发让位） | 判定纯函数正反例：全屏、最大化、跨屏、部分覆盖、桌面宿主类名 | 未改的合并/密度布局测试 |
| 让位不恢复或 z 序抖动 | 状态迁移单元；实际路径：全屏窗口激活 → 让位 → 退出全屏/切换焦点 → 恢复 | — |
| 多屏串扰 | 判定按显示器归属的单元用例 | 既有每屏一栏逻辑 |
| 既有桌面行为回归 | 布局/交互定向层（任务栏仍可点击、置前、重停靠） | 设置、更新、权限矩阵不重复 |
| 发布错配 | 准确候选晋升、附件核对及真实公开更新 | 既有发布闭环 |

布局与交互之外的实现未改则不重测对应矩阵。发布步骤完成后才能标记公开交付。
